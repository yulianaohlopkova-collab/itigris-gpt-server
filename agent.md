# agent.md — MVP ИИ-аналитика продаж «Очкидалинзы»

## 1. Роль агента

Codex-агент доводит проект до рабочей MVP-версии ИИ-аналитика продаж для «Очкидалинзы».

MVP должен работать как цепочка:

реальные входные данные → расчет сигналов → управленческий weekly output.

## 2. Цель MVP

Первая версия должна:

- принимать продажи из DataLens / Google Sheets / CSV-выгрузок;
- использовать ITigris `remoteRemains/list` только для остатков и товарной структуры;
- анализировать план-факт, салоны, сотрудников, категории и отклонения;
- выдавать отчет с сигналами, проблемами, гипотезами и фокусом для Коммерческого директора и Тренеров.

## 3. Текущая архитектура

- `server.py` — FastAPI API для Render/GPT Actions.
- `analytics.py` — детерминированная MVP-логика weekly output.
- `scripts/extract_ods_mvp.py` — извлечение обезличенных агрегатов из `source_docs/ODL_dashboard.ods`.
- `scripts/run_weekly_report.py` — запуск аналитики из `data/input`.
- `data/input/*.csv` — единый входной формат MVP.
- `reports/weekly_output_2026-04-01_2026-04-26.md` — первый прогон на реальных данных.
- `prompts/weekly_sales_analyst.txt` — рабочий prompt для LLM-слоя.
- `openapi.yaml` — чистая схема для GPT Actions.

## 4. Источники данных

Продажи:

- DataLens / Google Sheets / ODS / CSV;
- текущий пример: `source_docs/ODL_dashboard.ods`;
- период первого прогона: 2026-04-01 — 2026-04-26.

Остатки:

- ITigris Optima `/{app}/remoteRemains/list`;
- категории `accessories`, `contactlenses`, `glasses`, `lenses`, `sunglasses`;
- ключ через Render env: `ITIGRIS_REMOTE_API_KEY` или fallback `ITIGRIS_API_KEY`.

Защита API:

- `ODL_SERVER_TOKEN`;
- GPT Actions должны передавать `X-ODL-Token`.

## 5. Обязательный output

Каждый запуск должен формировать markdown-отчет:

1. Краткая картина периода
2. Ключевые сигналы
3. Проблемные зоны
4. Точки роста
5. Гипотезы причин
6. Фокус для Коммерческого директора
7. Фокус для Тренеров
8. Ограничения по данным
9. Следующий шаг

Output не должен быть пересказом цифр. Он должен говорить, куда идти и на что влиять.

## 6. Входной формат MVP

Папка `data/input`:

- `sales_period.csv` — салонные метрики периода;
- `plan_fact.csv` — план-факт выручки;
- `employees.csv` — агрегаты по сотрудникам без клиентских персональных данных;
- `categories.csv` — ОЛ, оправы, Better/Best, крупные линзы, фокусные категории;
- `training.csv` — optional, пока пустой шаблон;
- `data_dictionary.md` — словарь полей и ограничений.

## 7. ITigris и МКЛ

МКЛ должны обрабатываться через категорию `contactlenses`.

Поддерживаемые фильтры:

- `manufacturer`
- `name`
- `color`
- `radius`
- `diameter`
- `dioptre`
- `cylinder`
- `axis`
- `add`
- `wearingPeriod`
- `inPack`

Русские алиасы фильтров поддерживаются в `FILTER_FIELD_ALIASES`.

Важно: `remoteRemains` возвращает остатки, а не продажи. Поэтому МКЛ-продажи в MVP фиксируются из sales input, а детализация по параметрам МКЛ проверяется отдельным слоем остатков.

## 8. Что уже сделано в MVP

- Сервер переписан без сломанных экспериментальных endpoints.
- Убран хардкод ITigris key.
- `/count/{category}` снова рабочий, не deprecated.
- `/count-real`, `/count-real-excel`, `/test-report` не включены.
- Добавлены protected `/openapi.json` и `/docs`.
- Добавлен `/sales/analyze`.
- Реальная ODS-выгрузка преобразована в CSV input.
- Первый weekly output сформирован на реальных данных.

## 9. Ограничения текущей версии

- Нет данных по возвратам, переделкам и ошибкам заказов.
- Нет надежной скидочной дисциплины.
- Нет полной структуры одного чека.
- Нет связки сотрудников с тренерами и фактов обучающих вмешательств.
- Нет детальной структуры продаж МКЛ по параметрам в sales input.
- Текущий первый отчет построен по факту 2026-04-01 — 2026-04-26, а не по полному апрелю.
